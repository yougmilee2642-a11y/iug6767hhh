# Фокус: сценарии записи после питча

## Причина и решение

Обнаружены воспроизводимые проблемы: «стрижка» не совпадала с «на стрижку»; фраза с несколькими фактами могла попадать в модель до серверного разбора; время до/после полудня определялось по оставшимся свободным слотам; неизвестные услуги защищались частными правилами. В текущем JSON демо стрижка есть. Какой именно snapshot был на питче, без сохранённого разговора неизвестно.

Добавлен слой `agents/booking_language.py`: ограниченный разбор услуг по каталогу и явным aliases, падежи русских названий, дата/время из фразы и корректировки. `booking_dialogue.py` ведёт предпочтения, проверяет календарь, выбирает только фактический слот, спрашивает недостающие поля и готовит предложение. `runtime.py` сохраняет provenance и выполняет запись только после подтверждения. Модель не должна быть единственным контроллером этой операции.

Это не обучение Qwen и не замена транскрибации. Для понятного структурированного запроса запись теперь может пройти вообще без вызова LLM. Для открытых вопросов модель остаётся нужна; её качество на всех темах этим не доказано.

## Проверяемые ветки

| Ветка | Действие |
|---|---|
| Услуга + завтра + время в первой фразе | Сохраняем все факты; проверяем календарь, не повторяем известные вопросы. |
| Услуга отсутствует | Говорим об отсутствии в каталоге, предлагаем выбрать опубликованную; не проверяем календарь чужой услуги. |
| Другая выбранная услуга | Сохраняем дату/время, пересчитываем доступность; название услуги не становится именем клиента. |
| Несколько услуг | Один явный выбор для одной записи, без молчаливого удаления второй. |
| «В пять» | Используем рабочие часы, не оставшуюся доступность. Если возможны и 05:00, и 17:00 — уточняем. |
| Занятое точное время | Сообщаем, что нет слота именно на это время; показываем до четырёх других вариантов. |
| «Не в 17, а в 19» | Старое предложение недействительно; новое время требует нового подтверждения. |
| Контакты в одной фразе | Явные декларации собираются до подготовки действия; provenance не заменяется догадкой модели. |
| Закрытый день / прошедшая дата | Не создаём слот и запись. |
| Ошибка календаря | Один ограниченный повтор чтения; без вымышленных слотов и без повторной записи. |
| Слот занят до подтверждения | Повторная проверка, отказ от записи в занятый слот, обновление календаря. |
| Отказ от записи | Предложение отменено; последующее «ага» не сохраняет его. |
| Просьба человека | Существующая policy передачи/ручной проверки; живое соединение не имитируется. |
| Плохое/пустое распознавание | Существующие ограничения речи; выбор модели и сегментации — отдельная работа. |

Служебный `booking_flow.step`: consent, service, date, employee, time, field:…, proposal, confirmation, calendar_retry, completed/stopped/escalated. Это объяснимый статус текущего процесса; не доказательство понимания любого русского высказывания.

## Evaluation

Проверка готовности относится к **составному агенту: модель + Runtime + инструменты**, не к интеллекту модели отдельно. Модель, слабая на записи, может быть компенсирована контроллером. Ошибку провайдера проверяем на действительно модель-зависимом вопросе, не требуем ошибку там, где модель не вызывается.

Adversarial-проверки отсутствующего телефона/выдуманного поля теперь могут инъецировать ошибочный вызов прямо в реальный executor только внутри изолированной базы. Он обязан реально отказать по provenance. Trace отмечает `isolated_executor_injection`; это не выдаётся за ошибку, сгенерированную живой моделью. Assertions не заменены автоматическим PASS.

## Проверки и пределы

`tests/test_booking_scenarios.py` — новые регрессии питча с включённым consent и провайдером, который запрещает обращение к модели. Существующие проверки provenance, подтверждения и Evaluation сохранены; ожидания, привязанные к обязательному вызову модели в новой серверной ветке, переосмыслены отдельно.

`scripts/rehearse-booking-engine.py` — текстовый прогон актуального Runtime с настроенным локальным provider, временной SQLite и вымышленными контактами. Не открывает микрофон, не пишет в рабочий календарь, не включает облачный AI.

Финальные проверки: 660 passed, 12 skipped; 27 новых сценарных регрессий. Обе текстовые репетиции прошли; запрос с питча дополнительно проверен через запущенный localhost без выполнения записи. Отчёт: `proof/booking-engine/QA.md`, расшифровка синтетической репетиции: `proof/booking-engine-rehearsal.json`.

Не покрыты универсально: произвольный сленг и сложные падежи, все даты/форматы времени, сложные отрицания, несколько голосов, групповая запись, автоматическая отмена/перенос старой записи и подтверждение личности. Неизвестные формулировки надо уточнять, а не интерпретировать молча. Перед пилотом нужен корпус реальных обезличенных реплик с ожидаемыми фактами и исходами, отдельные оценки распознавания и LLM, нагрузочные испытания и живой календарь бизнеса.
