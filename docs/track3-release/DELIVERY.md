# Доставка уведомлений и SMTP

По умолчанию работают внутренний центр и локальные EML. Ничего не отправляется
во внешний аккаунт. Транспортные тесты используют вымышленные адреса и дублёры;
подключение настоящих сервисов агент не выполнял.

## Telegram / Битрикс24

Серверный администратор задаёт (в окружении, вне git):

- `CALLWISE_LOCAL_ONLY=false`, `CALLWISE_CLOUD_INTEGRATIONS_ENABLED=true`,
  `MEETINGS_NOTIFICATION_DISPATCH_ENABLED=1`;
- `MEETINGS_PUBLIC_URL=https://…` без логина/пароля/параметров;
- Telegram: `TELEGRAM_BOT_TOKEN` и JSON-словарь
  `MEETINGS_TELEGRAM_RECIPIENTS` с ключами локальных ID пользователей и
  положительными ID **личных** чатов. Группы не поддерживаются;
- Битрикс: `MEETINGS_BITRIX_ENABLED=1`, `MEETINGS_BITRIX_WEBHOOK`, проверенный
  `user_external_ids` mapping (`connector=bitrix24`), см. CRM_MOCK.md.

Сам пользователь открывает «Уведомления», включает канал, проверяет адресата
и ссылку в предпросмотре, подтверждает. Отправляется только фиксированное
общее уведомление и ссылка `/meetings`; клиентские имена, содержание задач,
документов и протоколов в сообщения не попадают. Метод Битрикс:
`im.notify.personal.add`. Telegram использует существующий TelegramClient,
HTTPS без redirect/env proxy; bot-token скрывается в HTTP-логах.

Очередь фиксирует версию настройки и отпечаток назначения. Перед доставкой
проверяются активность пользователя, объект/ACL, read_at, настройки и получатель.
Прочитанные, старше 24 часов, изменённые или неподтверждённые назначения
отменяются. Старые локальные очереди не начинают отправляться после добавления
ключа. При изменении mapping/configuration нужен новый preview/confirm.

Worker сначала фиксирует `sending` отдельной транзакцией, затем вызывает
провайдер вне write-lock и сохраняет результат. Таймаут/оборванный `sending`
становится `uncertain`; автоматического повторения нет. `failed`, `cancelled`
также терминальные. Перед ручным восстановлением нужна сверка с сервисом.

## SMTP приглашения

Дополнительно `MEETINGS_SMTP_ENABLED=1`, `MEETINGS_SMTP_HOST`,
`MEETINGS_SMTP_PORT` (465 по умолчанию), `MEETINGS_SMTP_USERNAME`,
`MEETINGS_SMTP_PASSWORD`, `MEETINGS_SMTP_FROM`, JSON
`MEETINGS_EMAIL_RECIPIENTS` (локальный ID → один адрес).
Транспорт только SMTP_SSL с проверкой сертификата и timeout 10с.
CLI `scripts/track3/start.py` намеренно включает local-only; для внешнего пилота
используется отдельный запуск продукта с явно заданным окружением, без этого
изолированного учебного launcher.

Даже после локального подтверждения встречи SMTP не запускается автоматически.
В «Мой календарь → Показать события и приглашения» организатор отдельно нажимает
«Проверить SMTP-отправку», видит отправителя, получателя, тему, текст, даты,
часовой пояс и ICS-вложение, затем подтверждает. Получатель должен оставаться
активным и иметь доступ к материалам; secret исключён. Любая смена адреса,
конфигурации, события или ACL отклоняет старый preview/очередь.
На приглашение допускается одна запись отправки. Повтор confirm не создаёт
новое письмо. Таймаут/перезапуск → uncertain без повтора. Статусы доступны
организатору через UI и `GET /api/meet/smtp-outbox`.
SMTP не распространяет протоколы или недельные дайджесты: они остаются
подтверждаемыми локальными EML. Массовой внешней рассылки нет.

`GET /api/meet/delivery-status` возвращает доступность каналов без секретов.
`POST /api/meet/calendar/outbox/{id}/smtp/{preview,confirm}` — дополнительное
согласие на внешнее письмо. Строки SMTP удаляются с приглашением/пользователем
или по `chat_days`. В таблице хранится отпечаток содержимого и статус,
не пароль или копия письма. Скачанные/доставленные копии находятся вне очистки БД.

Проверки: `tests/test_track3_delivery.py`, `test_track3_operations.py` и HTTP
с закрытыми каналами. Живые Telegram/Bitrix/SMTP — NOT RUN.
