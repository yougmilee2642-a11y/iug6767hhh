# Политика данных · состояние v2

Прототип использует только синтетические данные. Действующий безопасный CLI и
его границы описаны в [RETENTION.md](RETENTION.md). Эта страница дополнительно
учитывает новые таблицы v2 и описывает действующий периодический worker (раз в 60 секунд при запущенном API).

|---|---|---|---|

Перед CLI-удалением остановить сервер. По умолчанию cleanup показывает dry-run;
нужны абсолютный путь, корректный тестовый маркер и `--confirm-delete`. Рабочая
`data/`, каталоги, симлинки и неопознанные файлы защищены. Удаление файла не
доказывает физическое стирание носителя, резервной копии, копии CSV или истории git.
Запрос «удалить мои данные» доступен пользователю. Администратор получает перечень локальных объектов, проверяет его в preview и подтверждает удаление. Сохраняются обезличенный пользователь для внешних ключей, аудит и объекты других владельцев; исполнитель в чужих задачах снимается. Внешние системы и резервные копии этим действием не удаляются.

По умолчанию MeetingLLM обращается к loopback Ollama. Разрешённый защищённый
remote gateway обрабатывает данные на машине хоста, а не на компьютере
пользователя браузера. Cloudflare-туннель добавляет внешнего посредника. Сроки
хранения и резервные копии шлюза определяет его оператор; их необходимо включить
в процедуру удаления. Эти режимы нельзя называть полностью локальными на машине
пользователя. Детали маршрута/авторизации: [RUNBOOK.md](RUNBOOK.md).

CRM mock: `integration_outbox` хранит маскированный preview, payload_hash,
подтверждающего, дату, статус и код ошибки; `mock_crm_objects` — отправленную
маскированную задачу/подтверждённые пункты протокола и их реплики. Они находятся
в той же выбранной тестовой БД и удаляются вместе с ней через защищённый cleanup.
Целевой срок для этих копий — как для результатов встречи (180 дней);
автоматический object-retention пока не реализован. Объекты реального портала
не создаются и их удаление не имитируется. `uncertain`/`failed` нельзя удалять
для обхода защиты от повторной отправки до ручной сверки.

## Новые локальные очереди и согласие

Личные assistant_conversations/messages/evidence хранят только маскированный
вопрос, проверенные результаты и идентификаторы источников;30 дней по умолчанию.
Чтение истории повторно проверяет ACL и актуальность источника. Неподтверждённое
предложение в чате/голосе не создаёт бизнес-объект.

В центре «Хранение» администратор меняет сроки через preview/confirm. Очистка
демо-объектов разрешена только для DB с точным .track3.json маркером. Она не
удаляет произвольные пути. Скачанные файлы остаются у получателя.

Уведомления по умолчанию внутренние. Опции email/Telegram/Bitrix создают только
локальную очередь общего текста без названий встреч и ПДн; внешних отправителей
в этой фазе нет. Письма протокола содержат маскированные подтверждённые пункты;
получатели и их ACL проверяются при confirm и скачивании. Physical EML создаются
в выбранном outbox с закрытыми правами, без перезаписи существующих файлов.
Отдельные копии EML не отзываются при изменении ACL — их удаляет владелец.

Bitrix REST включается явно. Внешний календарь получает время и сопоставленные
ID участников, общее название «Встреча CallWise», без содержания/названия встречи.
Календарная очередь фиксируется до HTTP; uncertain блокирует повторную отправку
и сохраняет занятость. Нужна ручная сверка у администратора. Календарь и CRM
не подключались к реальным аккаунтам при разработке.

E7: media_jobs хранит статус и проверяемый черновик; media_segments содержит
распознанный текст. По истечении transcript_days удаляются и utterances,
и media_segments, а не только аудио. calls ссылается на confidential-встречу;
агент видит только свои звонки, head/lead — свой разрешённый scope, технические
роли не получают текст. Нет распознавания личности по голосу: метки сопоставляет
пользователь. Чек-лист/темы/риск — объяснимые правила с цитатами; речь не
используется для оценки эмоционального состояния или производительности людей.
