# Поиск и QA: SQLite FTS5 с правами до ранжирования

`GET /api/meet/search?q=…` использует FTS5/BM25 вместо подстрочного обхода.
Те же правила ранжирования применяются к кандидатам knowledge QA. Содержательные
ответы QA по-прежнему требуют модели; сам поиск работает без модели.

1. SQL-предикат `access.predicate(..., model=True)` отбирает разрешённые документы.
   При контексте встречи SQL дополнительно проверяет связь документа со встречей.
   Admin/auditor не могут выполнять контентный поиск. Secret не индексируется и
   не появляется в snippet; отдельное чтение файла владельцем сохранено.
2. QA проверяет дату, именованный контекст, минимальную релевантность, границы
   цитаты и бюджет контекста **до** top-k. Повреждённые/неподходящие источники
   не вытесняют допустимые. Фильтры инъекций и маскирование перед LLM сохранены.
3. Создаётся TEMP FTS5 индекс только из прошедших отбор фрагментов. Таким образом
   даже BM25 corpus statistics не зависят от чужих закрытых документов. Индекс
   удаляется в finally и не сохраняется в основной схеме БД. Роль/ACL не кэшируются.
4. Русская нормализация — существующие words/lexeme, включая ё/е и окончания.
   MATCH получает только нормализованные слова в кавычках и связанные параметры;
   пользователь не задаёт SQL, FTS-операторы или имена столбцов. Для ручного поиска
   требуется совпадение всех терминов; для QA — прежний порог релевантности и BM25
   среди допустимых кандидатов. Числовые anchors QA остаются обязательными.
5. Ответ ссылается на исходные ID/полный текст, не на копию из индекса. Поиск
   возвращает source_at загрузки. QA повторно проверяет цитаты и доступ по прежнему
   контракту. Изменение текста/прав учитывается уже следующим запросом.

Ограничения: индекс пересобирается на запрос, поэтому это не оптимизация для
миллионов фрагментов. Для 54 демо-документов выбран проверяемый способ изоляции
статистики. TEMP storage управляет системная сборка SQLite; это не гарантированное
удаление данных с носителя. В production нужны согласованная политика temp storage
и измерение большого корпуса. Отдельных постоянных индексов/кэшей/эмбеддингов нет.
Новая библиотека и `load_extension` не используются. Если FTS5/хранилище недоступны:
503 `search_unavailable`/`storage_unavailable`, безопасный аудит, без скрытого fallback.

Версии/valid_until, выдержки и diff описаны в [DOCUMENTS.md](DOCUMENTS.md).
По умолчанию SQL исключает устаревшие редакции при наличии доступного потомка;
`include_history=true` включает историю. В контексте встречи учитываются явно
прикреплённые редакции. Противоречия остаются отдельной задачей E6.4.
FTS не доказывает актуальность или истинность текста. Результаты
старого live QA нельзя переносить на новое ранжирование: хост повторяет LIVE_CHECKS.

Проверки: `tests/test_track3_fts.py`, knowledge retrieval/hardening, frozen v2
evaluator на scripted double. Реальные модели не запускались. Первичные источники
формата/алгоритма: [SQLite FTS5](https://www.sqlite.org/fts5.html) и
[документация CPython sqlite3](https://docs.python.org/3/library/sqlite3.html).
