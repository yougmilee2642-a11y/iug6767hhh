# Callwise: решения рисков клиента и границы реализации

14 октября 2026. Реестр основан на текущем коде, а не на обещаниях пилота. Исходный список содержит пропуски и смешанные пункты; ниже все названные проблемы сгруппированы без придуманных пунктов.

**Статусы:** реализовано — конкретная защита есть в коде и тестах; ограничено — есть безопасный обход/ручной процесс, но не полная функция; внешний этап — нужны инфраструктура, доступ, материалы или утверждение бизнеса. Regex-правила — консервативные примеры, не доказательство понимания всех формулировок.

Техническая кнопка демо не означает юридическую готовность. Уже совершённые операции и переданные данные нельзя автоматически отменить. |

Уверенное ошибочное распознавание ещё возможно. |
| 6. Другие сотовые операторы | Номера не фильтруются по МТС: валидатор проверяет формат, не принадлежность оператору. | Входящие с сетей других операторов проверить на реальной линии/АТС; телефонии сейчас нет. Не обещать доступность по всем операторам до теста. |

Не обучать модель автоматически на неподтверждённых звонках. |

## Реализация

- `services/customer_safety.py`: gate, отказ/отзыв, лимиты, явные риск-интенты, минимальный аудит кодов без исходного текста секретов.
- `agents/models.py`: safety defaults и ограниченные параметры; runtime применяет серверные guards до LLM/tools. При отказе до согласия отправленный текст не добавляется в историю.
- `services/safety_api.py`: выбор согласия и очередь менеджера под существующей owner-защитой.
- `services/review_requests.py`, таблица review_requests: reason/status + reference на исходный разговор; нет автоматического CRM update, вызова сотрудника или исходящего звонка.
- `static/privacy-consent.mjs`: отдельный выбор с отказом по умолчанию фокуса, до getUserMedia. Входной текст не является автоматическим согласием.
- `/static/safety.html`: ручные запросы в кабинете; смена статуса не выполняет внешнее действие.
- `services/booking_service.py`: явные алиасы услуг; текущие расписание/confirmation остаются источниками записи.
- Уведомления: без consent доставка не запускается; ожидающие Telegram отменяются после отказа через API и текстового отзыва. Worker повторно проверяет consent перед отправкой. Уже отправленное/в процессе передачи нельзя «забрать обратно».

Старые активные сессии без safety snapshot нужно завершить и начать заново. Защиты включены по умолчанию; `CALLWISE_CONVERSATION_SAFETY=false` предусмотрен только для legacy-изолированных тестов. Не отключать для демонстрации реальным клиентам. Старые unit fixtures не доказывают consent: новые `tests/test_customer_safety.py` отдельно проверяют полный включённый policy.

Симулятор и provider diagnostics принимают техническое демо-согласие явно только внутри изолированной базы с вымышленными данными. Источник такого решения отмечается `isolated_synthetic_evaluation`; это не согласие настоящего клиента. Защиты интентов и действий продолжают работать. Изменённое поведение может дать FAIL старому сценарию — результат не подменяется успешным.

## Настройка профилей / алиасов

```json
{
  "employees": [{"id":"anna","name":"Анна","public_profile":{"approved":true,"specialization":"Маникюр","experience":"5 лет"}}],
  "service_aliases": {"manicure":["ногти","обработка ногтей"]}
}
```

Это элементы business.knowledge, не произвольные инструкции клиента. Алиас должен ссылаться на service ID (или legacy точное имя). Public profile используется только для чтения. Политика safety находится в AgentConfig: notice/notice_version/max_turns/max_minutes/off_topic_limit/abuse_limit. Для текущего демо не назначен утверждённый юридический документ.

## Приоритет до пилота

1. Утвердить правовую схему бизнеса, условия роли Callwise/МТС, согласие/альтернативное основание, хранение и передачи. Тесты — только вымышленные данные.
2. Получить тестовую телефонию и CRM/календарь бизнеса; проверить реальный перевод, разные операторы и codec.
3. Добавить identity verification и менеджерский change/cancel workflow, а не свободное редактирование по номеру.
4. Провести голосовой benchmark: шум, отрицания, цифры, несколько говорящих, длинные паузы, время ответа; проверить лицензию TTS и заменить при необходимости.
5. Настроить очередь/мониторинг/backup, tenant isolation, права/аудит, реальные сценарии unknown и согласованную обработку отзывов во всех очередях.

Юридические материалы для согласования, не готовое заключение: [НЦЗПД Беларуси](https://cpd.by/) и [Закон Республики Беларусь № 99-З](https://pravo.by/document/?guid=12551&p0=H12100099). Полный текст официальных страниц во время работы не удалось получить (503/403), поэтому конкретные требования закона здесь не объявляются проверенными или выполненными. Для структуры согласия также изучены опубликованные материалы МТС; российские правила не подменяют белорусские. Правовую схему должен подтвердить ответственный бизнеса.
