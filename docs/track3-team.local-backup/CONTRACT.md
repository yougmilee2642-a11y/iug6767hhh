# Контракт расширений трека 3 — стартовая версия

Это проектный контракт, а не описание уже существующих endpoints. Префикс `/api/meet`, signed-cookie `cw_meet_user`, ошибки `{code, detail}` сохраняются. Старое API продолжает работать; новые поля добавляются совместимо. После начального согласования этот файл редактирует только Codex 3.

## Общие правила

- Транспортные даты/время — ISO 8601 с offset; сервер хранит aware UTC, UI показывает Europe/Minsk. Для календаря длительность в минутах, интервалы `[start, end)`. Срок задачи `due` остаётся календарной датой `YYYY-MM-DD`; просрочка считается по дате Europe/Minsk, статус `done` исключается. Существующие статусы `open|in_progress|done` сохраняются.
- Source: `{kind: "document"|"utterance"|"metric"|"task", id: string, title: string, source_at: string, quote?: string, locator?: string}`. Документ: `id=F12`, реплика `id=U12`; `source_at` — дата исходного документа/встречи, не дата генерации ответа. Метрика имеет идентификатор строки витрины, актуальность и формулу. Для источников KPI/задач нужен защищённый resolver, не произвольный URL.
- `GET /api/meet/sources/{kind}/{id}` → `{source, data}` только для `metric` и `task` (Codex 2). Для document/utterance использовать существующие fragment/utterance endpoints. Все resolver заново проверяют ACL.
- `401` нет входа, `403` роль не разрешает действие на доступном объекте, `404` чужой/отсутствующий объект, `409` stale/conflict, `422` ввод, `503 model_*` модель. При отказах сервер записывает безопасный аудит.
- Читающая роль: доступные встречи/материалы/QA/сводка; управляющая: дополнительно правки протокола, подтверждение/изменение задач и приглашения. Конкретные capability keys фиксирует Claude, `/me` возвращает `capabilities: string[]`; UI использует их, сервер проверяет независимо. Существующие irina/petr остаются совместимыми.
- AI не получает инструментов записи. Все фрагменты проверяются до передачи модели; цитаты сверяются с хранилищем. Модель не выбирает ACL, пути файлов или адреса получателей.
- Preview для значимых действий → `confirmation_id`, `expires_at`, полный нормализованный предпросмотр. Confirm принимает только token и ключ идемпотентности, а не подменяемый payload. Token связан с пользователем, действием, объектом и его версией; сервер повторно проверяет права, версию и конфликт. Два одновременных confirm дают один результат. Cancel не создаёт событие/приглашение/задачу и не меняет целевой объект (безопасная запись аудита разрешена).

## Claude: календарь и ядро

- `POST /calendar/slots` `{participant_ids: int[], range_start, range_end, duration_minutes, timezone: "Europe/Minsk"}` → `{slots: [{start_at,end_at}], timezone}`. Пользователь видит доступность, но не название чужого события. Участники — ID из тестового справочника, не свободный адрес электронной почты.
- `POST /calendar/preview` `{meeting_id, participant_ids, start_at, duration_minutes}` → `{confirmation_id, expires_at, preview: {meeting_id,title,start_at,end_at,participants,invitations,provider:"mock"}}`.
- `POST /calendar/confirm` `{confirmation_id, idempotency_key}` → `{event, invitations, already_confirmed}`. Приглашения — локальный outbox; внешних писем нет. Calendar confirm одновременно привязывает расписание к встрече.
- `GET /calendar/events` → `{events: [...]}` — только видимые события; чужая занятость для подбора слотов не раскрывает детали.
- `POST /tasks/{id}/preview` `{changes:{status?,assignee?,due?}}` → общий preview; `POST /tasks/{id}/confirm` → `{task, already_confirmed}`. Старый PATCH не должен оставлять обход подтверждения: Claude и Codex 1 совместно переводят интерфейс на новый поток, PATCH без подтверждения отвечает понятной ошибкой. Создание задач из протокола сохраняет текущий `/protocol/confirm`; UI показывает точный предпросмотр выбранного перед отправкой. Внешние интеграции не вызываются.
- `POST /feedback` `{meeting_id?, answer_id?, target_type, target_id, rating:"useful"|"incorrect", comment?}` → `{feedback_id}`. Проверить доступ к объекту; хранить только необходимое, comment ≤1000 символов. Чужой target не принимается.
- Протокол сохраняет `items`; добавить `kind:"risk"` и `summary: Claim[]` с проверяемыми цитатами. Старые kind/outcome не менять. Статусы предложения по-русски: принято/отклонено/обсуждалось. Непроверенный вывод помечается «требует уточнения».
- `prepare` дополнительно возвращает `open_tasks: Task[]` только из доступных связанных встреч и вопросы по ним; незакрытые задачи не смешивать с фактами документов без источника.
- Claude регистрирует `meetings.knowledge.api.router()` и `meetings.management.api.router()` в `install`. Импорт до появления модулей не должен ломать первый самостоятельный PR: registration переносится в интеграционный коммит после поставки модулей.

## Codex 2: знания

- `POST /qa` `{question: string, meeting_id?: int}` → `{answer_id, status:"grounded"|"insufficient_data", answer, claims:[{text,sources:Source[]}], sources:Source[], generated_at, model}`. В `grounded` каждая фактическая claim с источником; `answer` собирается из проверенных claims, не из дополнительного непроверенного текста модели. Для `insufficient_data` — честный отказ без выдуманного ответа.
- `question`: 1–2000 символов; лимиты кандидатов и контекста документированы. `meeting_id` ограничивает документы доступными приложенными материалами встречи, саму встречу также проверить. Глобальный режим ищет только доступные документы.
- Переиспользовать `MeetingLLM.json`; параметры и валидация ответа в новом модуле. При необходимости FTS SQLite или простой ранжированный поиск; PostgreSQL/pgvector/новый orchestration framework не обязательны.
- Хранение answer/session и таблицы feedback-preview согласуются с Claude на старте; сохраняются ID источников и минимальные данные для проверки прав. Нельзя выдавать старый сохранённый ответ после отзыва доступа к его источникам.

## Codex 2: управленческий обзор

- `GET /overview?as_of=<aware-ISO>` → `{as_of,generated_at,metrics:[{key,label,value,unit,formula,source:Source}],overdue_tasks:Task[],summary:[{text,sources:Source[]}],warnings:string[]}`.
- Минимум: открытые задачи, просроченные задачи, заказы в срок (%), брак (%), загрузка производства (%). Первые две из реестра разрешённых задач; последние три из синтетической производственной витрины с ACL, не константы интерфейса. Это сводка трека 3, не все 10 KPI трека 1.
- Сроки и формулы задокументировать; при нулевом знаменателе null и понятное предупреждение. Деньги при добавлении имеют валюту. Сводка может быть детерминированной: генерация текста моделью здесь необязательна.
- Строки витрины содержат source_id, as_of, scope/ACL и исходные числители/знаменатели. Состав таблиц и миграций согласовать с Claude; Codex 3 получает формат fixtures для seed.
- Чужие метрики и задачи исключаются до агрегирования. Сводка и resolver не должны позволять обойти права через известный id, дату или query-параметр.

## Аудит и передача

Claude предоставляет расширение `store.audit` с request/correlation ID и безопасной структурой: actor, at, action, object type/id, result, source IDs, proposal/confirmation ID, model/error code. Codex 2 вызывает общий audit для QA/overview, Codex 3 проверяет события. Текстовые вопросы хранятся в маскированном виде/минимизированном представлении по политике, токены и полный контекст в журнал не пишутся. Отказ должен пережить rollback основной транзакции.

Для каждого нового API владелец передаёт интегратору JSON примеры success/empty/forbidden/error и точную команду тестов. Владелец UI делает фикстуры по этому контракту и после интеграции проверяет настоящий API.
