## Как выдать задания

Каждому передать этот README, `CONTRACT.md` и ровно его файл задания. Полные вводные для вставки в чат находятся в `CLAUDE.md`, `CODEX_1.md`, `CODEX_2.md`, `CODEX_3.md`. Все четверо читают общий контракт до изменений.

У каждого — отдельный clone или worktree, отдельная ветка, `.venv`, `.env` и `MEETINGS_DB_PATH`. Даже на одном компьютере нельзя одновременно работать в одной папке: переключение ветки меняет файлы всех агентов. Нельзя совместно использовать живую SQLite. Нейросеть может быть общей через авторизованный шлюз; ключ передаётся лично, не в PR.

Ветки: `codex/track3-ui`, `codex/track3-knowledge-overview`, `codex/track3-release`, `claude/track3-core-calendar`. База всех веток — указанный SHA. Если до старта main продвинулся, интегратор сначала фиксирует новый общий SHA и повторяет базовые проверки; никто не выбирает базу самостоятельно.

Пример для отдельного клона (исполнитель подставляет свою ветку):

```powershell
git clone --recurse-submodules https://github.com/yougmilee2642-a11y/iug6767hhh.git Callwise-track3-ui
Set-Location Callwise-track3-ui
git switch -c codex/track3-ui cb2614b86f3b83636e670c83a0afb8f4c9d6c3c3
```

Папку с этим пакетом заданий также нужно передать исполнителям: сейчас это локальные файлы, они ещё не опубликованы на GitHub. Codex 3 первым отдельным коммитом публикует пакет в своей ветке; остальные получают эти файлы или SHA этого коммита до начала работы. Исходный код базы при этом не меняется.

## Владение файлами: правило без конфликтов

Каждый меняет только пути из своего задания. Всё не указанное — вне спринта. Особенно `app.py`, `providers/*`, ASR и старый кабинет: никто не меняет их без согласованной передачи конкретного файла одному владельцу. Расширения роутеров подключает Claude через существующий `meetings/api.py:install`; нового изменения `app.py` не требуется.

Все таблицы, индексы, миграции и сериализаторы общей БД принадлежат Claude (`meetings/store.py`, при необходимости `meetings/migrations/`). Codex 2 проектирует нужные данные, передаёт заявку Claude, но не добавляет альтернативную схему/БД и не редактирует store. Codex 3 загружает тестовые данные только после миграций Claude. Версионированные миграции должны работать на существующей базе, не только на пустой.

Старые `docs/MEETINGS_API.md` и `docs/MEETINGS_HANDOFF.md` описывают прежнее разделение на двух исполнителей. Для этого спринта действует этот четырёхсторонний план; старые документы не дают права редактировать чужую зону. Общую документацию/API обновляет только Codex 3 по описаниям владельцев.

Просьбы в другую зону записываются в свой `docs/track3-handoffs/<executor>.md` (каждый создаёт только свой файл): нужное изменение, причина, интерфейс, приёмочный тест, блокирует ли работу. Ни общего одновременно редактируемого журнала, ни правок чужих файлов «на одну строку».

Контракт фиксирует форму API до реализации. Изменение контракта: автор пишет предложение в свой handoff; интегратор согласует с затронутыми владельцами и единолично правит `CONTRACT.md`. Ответ потребителя не угадывается по чужому незавершённому коду.

## Порядок выполнения и объединения

1. Старт: все фиксируют базу и зоны. Claude и Codex 2 сразу согласуют таблицы/миграции и registration новых роутеров; Codex 3 сверяет DTO для данных/оценки. Это короткий контрактный этап, без переписывания приложения.
2. Все работают параллельно: UI на фикстурах контракта; knowledge/overview на тестовой БД; Claude на ядре и календаре; release на датасете, оценщике, запуске и LLM. Не ждать завершения одного агента, чтобы начать свой пакет.
3. Claude выпускает первый небольшой PR: права, миграции и точки подключения. Codex 3 объединяет его в `codex/track3-integration` от общей базы. Затем объединяет готовый knowledge/overview и календарную часть Claude, затем UI. PR release можно переносить раньше частями; итоговые данные и оценка идут после схемы.
4. Объединение — только интегратором, без push/force-push в main. Исполнители пушат свои ветки и открывают PR. Для интеграции применяются merge-коммиты с сохранением истории. После начала общей проверки не делать rebase уже объединённых веток: исправления — новыми коммитами.
5. Каждый владелец исправляет дефекты своей зоны. Интегратор не чинит чужую бизнес-логику молча. Зависимый PR помечается base/зависимостью, чтобы одинаковые коммиты не попадали в выпуск повторно.
6. На интеграционной ветке: тесты, чистый запуск, реальная модель, браузер и сценарий 5–7 минут. После успешных проверок — итоговый PR в main, объединяет назначенный сопровождающий репозитория. GitHub хранит код; это само по себе не размещает работающий FastAPI-сервис. Для этого MVP достаточно воспроизводимого локального запуска, если отдельный хостинг не согласован.

Запретить `git add .`, `git reset --hard`, `git clean -fd`, force-push и массовое форматирование чужих файлов. Добавлять в коммит явные пути; перед push смотреть `git diff --cached --stat` и `git diff --cached --check`. Весов, env, ключей, рабочих БД и реальных данных в Git нет.

## Когда работа считается законченной

- Все шесть сценариев §7.2 выполняются через русский интерфейс; календарь и приглашения явно тестовые.
- Две роли различаются серверными полномочиями; чужой документ не попадает даже в контекст модели; отказ записан в аудит без раскрытия его содержимого.
- Значимое действие имеет предпросмотр и явное подтверждение. Отмена оставляет целевые объекты без изменений; повтор подтверждения не создаёт дубль.
- Каждое утверждение имеет доступный источник и дату либо явную отметку отсутствия основания. Задачи и протокол связаны с исходной встречей/репликой.
- На контрольных расшифровках найдены ≥80% явно сформулированных задач; отдельно показаны ложные задачи и ошибки владельца/срока. Есть результаты реальной модели, не только тестового double.
- ≥20 документов, 3 расшифровки, тестовый календарь, задачи, KPI и разные уровни доступа; повторная загрузка воспроизводима.
- Сохраняются данные после перезапуска; ошибки модели/сети понятны и не уничтожают ввод; проверены клавиатура и узкий экран.
- Инструкция воспроизведена другим участником; есть API, архитектура, лицензии, хранение/очистка, отчёт, вопросы с эталонами, демо на 5–7 минут и содержание презентации до 10 слайдов.
